## Tools

- **pytongue**: a `.py` file imported through the `pytongue/register` preload; one long-lived `uv run` worker, NDJSON over a private pipe, every call validated by Pydantic.
- **pytongue (no validation)**: a hand-written ~30-line Python worker started with `uv run` and spoken to over NDJSON with `child_process`; no generated module and no validation.
- **python-shell**: python-shell 5 in persistent JSON mode (`send()` and `on('message')`) against the same minimal worker, started with the venv's `python` (no uv).
- **pythonia**: pythonia drives a Python process with its own IPC protocol and returns proxies; `PYTHON_BIN` points at the venv.
- **pymport (in-process)**: an embedded CPython bundled with the package, loaded as an N-API addon: in-process, no IPC, synchronous; payloads are converted to and from real Python objects. (embedded CPython 3.12.2)
- **pyodide (WASM, Python 3.14)**: CPython compiled to WebAssembly, in-process and synchronous; a different interpreter (3.14) from the other rows; payloads are converted to and from real Python objects. (Pyodide 314.0.8 (WASM CPython 3.14.2))
- **spawn per call**: a fresh `python` process per call (`child_process.spawn` on Node, `Bun.spawn` on Bun), payload on stdin; uses the venv's `python`, not `uv run`, so uv's startup does not dominate. Iteration counts are capped.
- **FastAPI + uvicorn (HTTP)**: a FastAPI app served by one uvicorn worker (`uv run --with fastapi --with uvicorn`, `async def` handlers) and called with `fetch` over loopback HTTP/1.1 keep-alive.
- **Native Python (floor)**: the same functions called directly in-process by a Python script timed with `time.perf_counter_ns`; one run, shown in both runtimes' tables for reference.

## Interpretation

- **What pytongue adds to a bare pipe (Node 24.22.3).** The p50 of `add(1, 2)` is 114 us for pytongue and 28.3 us for the hand-written worker started the same way: pytongue is 4.0x slower than the bare bridge, 85.6 us more per call, and 9,221 against 66,519 sequential calls/s. That gap is everything the library does that the raw worker does not: encoding the call, Pydantic validation of the arguments and of the result, handing sync functions to a dedicated thread, and the generated module's promise bookkeeping. This benchmark does not separate those costs.
- **What pytongue adds to a bare pipe (Bun 1.4.4).** The p50 of `add(1, 2)` is 112 us for pytongue and 13.0 us for the hand-written worker started the same way: pytongue is 8.6x slower than the bare bridge, 99.2 us more per call, and 12,569 against 63,432 sequential calls/s. That gap is everything the library does that the raw worker does not: encoding the call, Pydantic validation of the arguments and of the result, handing sync functions to a dedicated thread, and the generated module's promise bookkeeping. This benchmark does not separate those costs.
- **The floor.** Calling the function directly in Python takes 0.13 us; the lightest IPC here (the no-validation worker) takes 28.3 us on Node, 221x more. Everything that crosses a process boundary pays a pipe round trip, JSON encoding and scheduling, so a call that does real work (the CPU scenario) hides that cost and a trivial call does not.
- **Against the other tools on Node.** pytongue's p50 is 7.6x slower than python-shell (15.0 us), 5.8x slower than pythonia (19.7 us), 4.1x faster than FastAPI + uvicorn (HTTP) (464 us). With 100 calls in flight pytongue reaches 22,508 calls/s, python-shell 233,877, pythonia 149,487, FastAPI + uvicorn (HTTP) 5,474. pytongue serializes sync Python functions on one worker thread, so concurrency adds little for `def` functions; `async def` functions run concurrently.
- **Cold start (Node).** pytongue takes 212 ms to the first result, 101 ms for the no-validation worker and 94.2 ms for a single fresh Python process: it pays `uv run`, the bridge import and the Pydantic import once, then amortizes them over the process lifetime. Pyodide spends 1,379 ms loading its WASM runtime before the first call. FastAPI plus uvicorn needs 318 ms to boot and answer.
- **CPU-bound work.** Bridged calls take 159 ms (pytongue), 160 ms (pythonia), 169 ms (python-shell) against 158 ms native: the work runs in the same CPython, so the bridge disappears into the noise. Pyodide needs 345 ms (2.2x native) because it is a WASM build of a different Python version. pymport, an embedded 3.12 build, takes 292 ms.
- **Large payloads (Node, 1 MB).** FastAPI + uvicorn (HTTP) 22.2 ms, python-shell 30.2 ms, pytongue (no validation) 31.6 ms, spawn per call 49.4 ms, pytongue 50.5 ms, pythonia 55.2 ms, pyodide (WASM, Python 3.14) 57.0 ms, pymport (in-process) 32,013 ms. Serializing, piping and parsing a megabyte of JSON dominates, so the per-call overhead that separates the tools on small calls stops mattering; in-process tools instead pay to convert the whole object graph.
- **The HTTP baseline depends on the client runtime.** The same FastAPI server answers `add(1, 2)` at a p50 of 464 us when called with Node's `fetch` and 215 us with Bun's (2.2x faster than Node), so part of any HTTP number here is the client, not Python.
- **Node versus Bun.** pytongue's p50 is 114 us on Node and 112 us on Bun (about as fast as Node), with cold starts of 212 ms and 157 ms. Tools that do not run: python-shell on Bun 1.4.4; pythonia on Bun 1.4.4; pymport (in-process) on Bun 1.4.4. pytongue and the plain `child_process`/`fetch` baselines are the ones that work on both.
- **Caveats.** One machine, one run, loopback only, no CPU pinning: read ratios, not absolute numbers, expect noise between runs, and treat differences under about 1.3x (the CPU rows included, where native runs once at the start) as inconclusive. Pyodide is Python 3.14 in WASM and pymport bundles its own 3.12.2, so their CPU rows compare different interpreters. The pytongue worker is started by `uv run` while python-shell and pythonia use the venv interpreter directly, which shows in the cold-start column and nowhere else. FastAPI is measured with `async def` handlers, one uvicorn worker and the default `h11` HTTP stack, which favours it over a typical sync-handler deployment.
