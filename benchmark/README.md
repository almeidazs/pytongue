# Benchmark: calling Python from Node 24 and Bun

Compares pytongue with other ways to call Python from JavaScript, on Node 24 and on Bun. The
output is [RESULTS.md](./RESULTS.md), committed and regenerated by one command. It runs on
demand only, never in CI.

## Run it

You need Node 24, Bun, uv and network access (the first run downloads npm packages, the
`pymport` binary, a Python 3.12 venv, and FastAPI and uvicorn through uv).

```bash
bun install --cwd benchmark   # optional: the driver installs on first run
bun run bench                 # full run, a few minutes, rewrites benchmark/RESULTS.md
bun run bench -- --quick      # fewer iterations, writes benchmark/RESULTS.partial.md
bun run bench -- --only pytongue,fastapi
```

`--quick` and `--only` never touch the committed `RESULTS.md`: they write `RESULTS.partial.md`
(ignored by git). Pass `--out <file>` to choose another path.

| Variable | Meaning |
| :--- | :--- |
| `PYTONGUE_BENCH_NODE` | Path to a Node 24 binary. Otherwise the Linuxbrew `node@24` and then `node` on `PATH` are tried. |
| `PYTONGUE_BENCH_PYTHON` | Python used by the venv-based tools. Default `benchmark/.venv/bin/python`, created with uv. |
| `PYTONGUE_BENCH_TIMEOUT` | Per-cell timeout in seconds (default 120). A cell that exceeds it is reported as `timeout`. |
| `PYTONGUE_UV` | The uv binary. |

The driver builds pytongue (`bun run build` at the repository root) when `dist/` is missing, and
links `benchmark/node_modules/pytongue` to the repository root, so the preload under test is
always the working tree.

## How it works

- `run.ts` is the driver. For every tool, runtime and scenario it starts `child.ts` in its own
  process group, reads `@@RESULT@@ {json}` lines from its stdout, and aggregates them. A crash
  (pymport on Bun panics inside the native addon) fails only that cell. Tools that cannot run are
  detected by running them: the table shows the first error line the process produced.
- `tools/<tool>.ts` are the adapters. Each exposes the same three Python functions (`add`, `echo`
  and `cpu`, defined in `python/bench.py`) behind the `Session` interface in `types.ts`.
- `scenarios.ts` holds the five scenarios, written once against that interface.
- `python/` has the shared functions, the hand-written NDJSON worker, the spawn-per-call script,
  the FastAPI app and `native.py`, the in-process floor.
- `report.ts` renders `RESULTS.md`, including the interpretation bullets, whose numbers are
  computed from the same results.

## Scenarios

1. **Cold start**: wall time from spawning the Node or Bun process to the first `add(1, 2)`
   result, median of 5 fresh processes after one discarded warm-up. The "client only" column
   leaves out the runtime's own boot.
2. **Small-call latency**: 2000 sequential `add(1, 2)` calls after 200 warm-up calls.
3. **Throughput**: 20 000 sequential calls, and 20 000 calls with up to 100 in flight (not
   measured for the synchronous in-process tools).
4. **Payload scaling**: `echo` of about 1 KB, 100 KB and 1 MB objects (a list of records).
5. **CPU-bound**: a pure-Python loop called 5 times.

## Reading the results

- Compare ratios, not absolute numbers: it is one machine, one run, loopback networking.
- Native Python is the floor for the small-call scenarios. Anything crossing a process boundary
  pays a pipe round trip, JSON encoding and scheduling.
- The `pytongue (no validation)` row runs a ~30-line worker with no Pydantic and no generated
  module, started with `uv run` like pytongue's own. The gap to the `pytongue` row is the cost of
  validation and the generated module.
- pymport (embedded CPython 3.12.2) and Pyodide (WASM CPython 3.14) are in-process: there is no
  IPC, calls block the event loop, and payloads are converted to real Python objects instead of
  serialized. Pyodide is a different interpreter, so its CPU row compares different builds.
- Spawn per call uses the venv's `python` directly, not `uv run`, otherwise uv's startup would
  dominate. Its iteration counts are capped, and the table says by how much.
- FastAPI is measured with `async def` handlers, one uvicorn worker and the default HTTP stack
  (`h11`), which favours it against a typical deployment with sync handlers.

## Caveats

- python-shell and pythonia need Node-specific child process behaviour that Bun lacks, and
  pymport's native addon uses libuv functions Bun does not implement. Those failures are real and
  may be fixed by newer Bun versions: the report records what happened on the machine it ran on.
- `PyObject.fromJS` in pymport grows roughly quadratically with the object size, so its 1 MB
  payload cell is a single call (the cell shows `n=1`).
- pytongue starts its worker with `uv run --with pydantic`, which resolves the environment on
  every start. That cost shows only in the cold-start column.
